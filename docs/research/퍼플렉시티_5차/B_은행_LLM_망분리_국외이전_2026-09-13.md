## 답변 원문

학기 프로젝트처럼 공개 법령, 국회 법안, 발행사 공시만 처리하고 개인정보나 개인신용정보를 입력하지 않는다면, 미국 서버의 외부 LLM API 사용이 개인정보보호법 제28조의8 및 신용정보법상 국외 이전 규율의 직접 대상이라고 보기는 어렵습니다. 다만 실제 은행 내부망에 붙여 도입할 때에는 전자금융감독규정 제15조의 망분리, 혁신금융서비스 특례 또는 제도화된 예외, 개인정보 및 개인신용정보의 국외 이전과 처리위탁, 클라우드 공급망과 접근통제, 출력 검증을 함께 충족해야 하므로 "외부 API를 무조건 쓸 수 있다"가 아니라 데이터 유형과 접속 구조별로 승인 구조를 설계해야 합니다.

확인 문장:
- "제15조(해킹 등 방지대책) ① 금융회사 또는 전자금융업자는 정보처리시스템 및 정보통신망을 해킹 등 전자적 침해행위로부터 방지하기 위하여 다음 각 호의 대책을 수립·운용하여야 한다." (law.go.kr)
- "SaaS는 전자금융거래법 제21조 및 전자금융감독규정 제15조에 따른 망분리 규제를 적용받지 않도록 명시된다." (fsc.go.kr)

사실: 제15조는 망분리 논의의 법적 근거 조문으로 사용된다.
추론: 은행의 내부 업무망에서 미국 소재 LLM API로 프롬프트와 RAG 검색문서를 직접 전송하는 구조는, 별도 특례나 적용 제외 근거가 없다면 제15조의 외부통신망 직접접속 차단 취지와 충돌할 가능성이 높다.

**공개 자료만 쓰는 경우**

| 질문 | 사실 | 추론 |
|---|---|---|
| 법령, 국회 법안, 발행사 공시만 RAG에 넣으면 개인정보보호법 제28조의8이 적용되는가 | 제28조의8은 개인정보의 국외 제공, 조회, 처리위탁, 보관을 규율한다 | 입력 문서, 사용자 프롬프트, 시스템 로그, 첨부파일에 개인정보가 전혀 없다면 해당 데이터 이전 자체는 제28조의8의 객체인 개인정보 이전이 아니다 |
| 신용정보법상 국외 처리 문제는 발생하는가 | 신용정보법은 신용정보, 특히 개인신용정보의 이용, 제공, 처리위탁을 규율한다 | 법령이나 일반 공시 자체가 개인신용정보를 포함하지 않고, 사용자가 고객정보를 입력하지 않으며, 로그에도 식별 가능한 개인신용정보를 남기지 않는 구조라면 개인신용정보 처리위탁 쟁점은 원칙적으로 발생하지 않을 가능성이 높다 |
| 그래도 남는 위험은 무엇인가 | 외부 API에는 입력 프롬프트, 검색된 청크, 메타데이터, 사용자 계정 정보, 접속 로그 등이 전송될 수 있다 | "지식베이스가 공개자료"인 것만으로 충분하지 않다. 사용자가 질의창에 고객명, 계좌번호, 상담기록, 내부 규정, 비공개 거래정보를 붙여넣지 못하도록 기술적 통제를 해야 한다 |

중요한 구분: 공개된 "발행사 공시"라도 개인 투자자 명단, 담당자 실명과 연락처, 서명, 이메일, 특정 자연인의 거래나 보유 내역처럼 식별 가능한 정보가 포함되면 개인정보 여부를 별도 검토해야 한다. 공개되어 있다는 사실만으로 개인정보성이 자동 소멸하는 것은 아니다.

| 계약 통제 | 모델사업자의 입력 데이터 학습 금지, 보존 기간, 삭제, 하위 수탁자, 침해사고 통지, 감사권, 국외 재이전 제한을 계약에 반영해야 함 |
| 보안 통제 | DLP, 프롬프트 필터, PII와 개인신용정보 탐지와 마스킹, 접근권한 최소화, 암호화, 감사 로그, 출력 필터가 필요 |
| 모델 위험관리 | 법령 개정일 자동 확인, 출처 기반 답변 강제, 환각 검증, 금지 답변 정책, 고위험 답변의 준법부서 검토 절차가 필요 |

### 최종 답변

공개 자료만 쓰는 학기 프로젝트 단계에서는, 법령과 국회 법안과 발행사 공시와 사용자 질의에 개인정보 및 개인신용정보가 전혀 포함되지 않도록 입력 차단과 로그 통제를 갖춘다는 전제 아래 미국 LLM API를 사용할 수 있다. 이 경우 개인정보보호법 제28조의8은 "개인정보"의 국외 제공, 조회, 처리위탁, 보관을 규율하고, 신용정보법도 신용정보 특히 개인신용정보 처리 문제를 다루므로, 순수 공개자료 자체는 그 규율 객체가 아닐 가능성이 높다. 그러나 은행이 내부 데이터를 붙여 도입하면 결론이 달라진다. 내부망에서 외부 API로 연결하는 행위는 전자금융감독규정 제15조상 망분리와 직접 관련되고, 생성형 AI 내부망 이용은 금융위가 혁신금융서비스 방식으로 개별 허용해 온 영역이다. 또한 프롬프트, RAG 청크, 로그, 운영자 접근을 포함한 데이터 흐름에서 개인정보와 개인신용정보의 국외 이전 또는 처리위탁이 발생할 수 있다. 따라서 은행 도입 단계에는 외부 API를 일률적으로 금지하거나 허용하기보다, 공개자료 전용 외부 API 구역과 개인정보와 개인신용정보와 비공개 내부문서용 폐쇄형 또는 특례 승인 구역을 분리하고, 필요하면 온프레미스 또는 국내 통제형 배포 모델을 병행하는 구조가 현실적이다.
