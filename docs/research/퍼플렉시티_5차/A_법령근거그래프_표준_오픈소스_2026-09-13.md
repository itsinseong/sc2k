**권장 URI 예시** (추론. ELI의 공식 한국 등록 URI가 아니라 공개 데이터셋용 설계 예시)

```text
# 법령 Work: 법 자체의 정체성
https://example.org/eli/kr/law/{law_id}

# 특정 공포본 또는 시행본 Expression
https://example.org/eli/kr/law/{law_id}/{promulgation_date}/kor

# 특정 조문 Fragment
https://example.org/eli/kr/law/{law_id}/{promulgation_date}/kor#art_15

# 조 제2항 제3호
https://example.org/eli/kr/law/{law_id}/{promulgation_date}/kor#art_15__para_2__point_3
```

추론: 조문 단위 URL의 fragment는 Akoma Ntoso eId와 일치시키고, 별도의 stable_id 또는 wId 계열 값을 유지해야 개정으로 조문 번호가 이동하거나 바뀌는 상황을 추적할 수 있습니다.

**X 제거 영향 분석 예시** (추론. 간선 방향을 "근거가 되는 노드 → 그 근거에 의존하는 노드"로 통일한 경우)

```python
import networkx as nx

def unreachable_after_removal(graph: nx.DiGraph, roots: set[str], removed: str) -> set[str]:
    """
    roots: 법령, 정부자료, 계류법안 등 최상위 근거 노드
    removed: 제거 가정할 노드
    반환값: 제거 전에는 루트에서 도달했지만, 제거 후에는 어느 루트에서도
            도달하지 못하는 노드
    """
    before = set()
    for root in roots:
        if root in graph:
            before.add(root)
            before |= nx.descendants(graph, root)

    g2 = graph.copy()
    g2.remove_node(removed)

    after = set()
    for root in roots - {removed}:
        if root in g2:
            after.add(root)
            after |= nx.descendants(g2, root)

    return before - after - {removed}
```

핵심:
- article_15를 제거했을 때 끊기는 노드만 알고 싶다면, 해당 조문을 삭제한 복사 그래프와 원래 그래프의 루트 도달 가능 집합을 비교한다.
- 하나의 규칙이 5층 근거 중 둘 이상으로 지지된다면, 한 출처 노드를 제거해도 규칙 노드는 계속 도달 가능할 수 있다.
- 이 방식은 "어떤 근거가 단일 실패점인가"를 보여주므로, 15개 공시 규칙의 증거 강도를 수량화하는 기반이 된다.
- nx.articulation_points()는 무방향 연결 그래프의 절단점 분석 도구이므로 방향성 있는 인용 및 근거 그래프에는 그대로 쓰지 않는다.

**최종 설계 판단** (추론): 공개 배포물은 하나가 아니라 셋을 동시에 낸다.
1. 원본 JSON. 현재 파이프라인과 완전히 호환되는 연구 데이터. 인용문 글자 일치 검사 결과와 원문 해시 유지.
2. Akoma Ntoso XML. 법령과 법안의 조, 항, 호, 목 구조를 재사용 가능한 표준 문서로 배포. eId와 버전별 expression으로 개정 이력 구조화.
3. Turtle 또는 JSON-LD. 문서, 조문, 인용문, 공시 규칙, 근거 층위, 검증 결과, 변경 이력을 그래프로 배포. FIBO는 금융 개념 연결에만 제한적으로 재사용. PROV 계열 메타데이터로 "누가, 언제, 어떤 원문에서, 어떤 인용을 추출했는가"를 표현.

LegalRuleML은 네 번째 산출물로서, 15개 규칙 가운데 실제로 기계 판정이 필요한 규칙만 선정한 뒤 도입한다. 현재 단계에서는 조문 원문을 규칙으로 완전히 변환하는 것보다, 인용문 원문 일치, 법적 상태, 시행일, 준비자산 비율, 수탁 분리, 상환 기한 같은 검증 가능한 조건을 별도 규칙으로 관리하는 편이 더 재현 가능하고 감사 가능성이 높다.

## 프롬프트 원문

```
나는 한국 원화 스테이블코인 준비금 공시 규칙 15개를 법령, 계류 법안, 정부 자료, 보도, 관행의 5층 근거에 연결하는 "근거 그래프"를 만들고 있다. 지금은 JSON 파일(문서 39건, 간선 110개)이고, 간선마다 원문 인용문이 붙어 있으며 인용문이 원문에 글자 그대로 있는지 코드로 검사한다. 이걸 공개 표준과 오픈소스로 올리고 싶다. 아래를 조사해 달라.

1. Akoma Ntoso (OASIS LegalDocML)
   - 조, 항, 호, 목을 노드로 표현하는 구조와 eId(요소 식별자) 명명 규칙의 원문 규격
   - 한국 법령이나 아시아 국가 법령에 적용한 공개 사례가 있는지
   - Python으로 Akoma Ntoso를 읽고 쓰는 오픈소스 라이브러리
2. ELI(European Legislation Identifier)와 유사한 법령 URI 체계. 한국 법제처의 법령ID 체계와 대응시킬 수 있는지
3. LegalRuleML — 법 조문을 규칙(조건, 결과)으로 표현하는 표준. 실제 도구나 사례가 있는지, 아니면 논문 수준인지
4. FIBO (EDM Council, Financial Industry Business Ontology)
   - 준비자산(reserve asset), 수탁기관(custodian), 발행사(issuer), 상환(redemption)에 해당하는 클래스나 속성이 있는지, 있으면 클래스 이름과 URI
   - 스테이블코인이나 디지털자산 관련 확장이 있는지
5. 규제 변경 추적(regulatory change management)의 공개 사례나 오픈소스. 예: 영국 FCA Digital Regulatory Reporting, 미국 Federal Register API, 유럽 EUR-Lex 변경 알림. 법안 상태를 기계적으로 추적하는 공개 구현이 있는지
6. 금융권 규제 지식그래프의 공개 논문이나 사례(은행, 규제기관, 벤더 무관). 어떤 그래프 DB나 온톨로지를 썼는지
7. Python 도구 비교: networkx, rdflib, pyoxigraph, kuzu. 노드 수천 개 수준 소규모 그래프에서 도달 가능성 질의("노드 X를 제거하면 도달 못 하는 노드")를 하기에 어떤 게 맞는지

출력 형식:
- 항목마다 원출처 URL, 발행 기관, 문서 날짜, 확인 문장 인용을 붙인다
- 사실과 추론을 분리한다. 추론이면 "추론"이라고 쓴다
- 못 찾으면 "못 찾음"이라고 쓴다. 지어내지 않는다
- 2차 블로그나 요약 글을 원출처 대신 쓰지 않는다. 표준 문서, 기관 페이지, 논문, 저장소만
- 마지막에 "이 프로젝트에 바로 쓸 수 있는 것 3개"를 이유와 같이 고른다
```
