1. 살아있는 추적

왜 실시간이 아니라 폴링인가

법제처, 의안정보시스템, Circle, SEC 어디에도 "바뀌었다"고 밀어주는 웹훅이 없다. 서버가 24시간 켜져 있어도 하는 일은 "가서 물어보기"다. 그러면 주기는 소스가 움직이는 속도에 맞춘다.

소스움직이는 속도주기확인하는 것
의안정보시스템빠르면 하루하루 1회 (회기 중 시간 단위 가능)법안 8건 상태(계류, 심사, 수정, 폐기, 통과), 정부안 제출 여부, 신규 발의
법제처 API몇 달하루 1회법령ID별 시행일자 변경
Circle transparency월 1회하루 1회최신 PDF 링크
SEC EDGAR N-MFP3월 1회하루 1회CIK 844779 최신 제출
해외 하위규정 (OCC, MAS)몇 달주 1회최종규칙 게시 여부. 참조층이라 우선순위 낮음

구조

watch/
  likms_bills.py    → 법안 8건 상태 + 정부안 검색 + 신규 발의 (fnSearch, data-bill-id)
  law_go_kr.py      → 법령ID별 시행일자 (OC stablecoin, DRF lawSearch)
  circle.py         → transparency 페이지의 최신 PDF 링크
  sec_nmfp.py       → CIK 844779 최신 제출
  state.json        → 4개 소스의 마지막 상태(해시, 날짜)

GitHub Actions cron 매일 1회
  → 4개 실행 → state.json과 diff
  → 차이 있으면: 커밋, 이슈 자동 생성, 파서 재실행, 시나리오 JSON status 갱신
  → 차이 없으면: 아무것도 안 함

시나리오 쪽 반응
  법안 통과   → 그 시나리오를 KR-law로 승격, 나머지는 보관
  법안 폐기   → 그 시나리오 회색 처리, 매달린 규칙은 공백으로 재판정
  신규 발의   → 시나리오 JSON 하나 추가 (값은 사람이 채움)
  내 제안(D-01~D-05)의 반증 조건에 걸리면 → 제안 고침

서버 없이 된다. Oracle Cloud는 분 단위가 진짜 필요해지면 그때. 이 프로젝트에는 그런 소스가 없다.

LLM은 어디에 쓰나

  • 감지기로는 안 쓴다. 퍼플렉시티 116행 중 6행이 틀렸던 그 방식이다.
  • 4층 보도 후보 수집에는 쓴다. 원래 제일 못 믿는 층이라 LLM이 긁어도 손해가 없고, 확정은 1~2층(법령, 법안 원문)에서 한다.
  • 하네스의 공격자로 쓴다. 간선이 바뀌거나 새 법안이 들어오면 CI가 Codex에게 "이 간선 무너뜨려 봐"를 시키고 반박을 이슈로 남긴다. 적대검증 3차를 손으로 한 것의 자동화.

3. 파서 출처 추적

지금 상태(scripts/parse_circle.py 확인): 원본 PDF는 보관, 숫자와 텍스트 몇 개(examination 여부, 기준 표준, 날짜, 1쪽 깨짐 플래그)를 JSON으로. pdftotext 전문은 안 남기고, 숫자가 몇 쪽 몇 줄에서 왔는지도 안 남긴다.

고치는 법: pdftotext -layout 출력을 줄로 쪼개면 줄 번호가 공짜다.

data/samples/Circle_USDC_Examination_2026-07.pdf
data/samples/Circle_USDC_Examination_2026-07.txt     ← 전문 그대로

reports.json의 숫자 하나:
{ "value": 64931234567, "page": 2, "line": 41,
  "raw": "TOTAL USDC RESERVE ASSETS AS OF JULY 31, 2026   $ 64,931,234,567" }

"모든 내용을 파싱"은 아니다. 파싱은 구조를 만드는 일이고, 5쪽 중 표 빼고는 회계사 상용구다. 저장은 하되 파싱은 안 한다. 산문에 억지로 구조를 씌우면 그게 오염이다. 좌표(bbox)까지 따는 pdfplumber는 사람이 찾아가는 데 줄 번호로 충분해서 과하다.

골드만 SecDB, JP모건 Athena는 비공개라 못 쓴다. 공개된 것 중 쓸 만한 건 셋.

5. 빈칸에서 LLM 검색 — RAG 방식과 은행 로컬 모델

RAG 방식

문서 39건에 벡터 DB는 과하다. 근거 그래프가 이미 검색 색인이다. 노드를 따라가서 인용문을 꺼내는 방식이고, 이름 붙이면 GraphRAG의 축소판. 벡터 검색은 corpus가 수백 건을 넘으면 그때.

억지가 안 되려면 조건 셋

  1. LLM은 노드 id로만 답한다. 화면은 LLM 문장이 아니라 그 노드의 검증된 인용문을 보여준다. LLM이 인용 안 한 건 안 뜬다
  2. 판정은 안 한다. "충족 같습니다"는 금지. 그건 규칙 엔진 몫
  3. corpus 밖은 답 안 한다. "모르겠다"가 정답인 경우를 허용

순서

5층 × 상태 × 날짜 필터 UI가 먼저다. 그게 없으면 LLM이 검색할 게 없고, 그게 있으면 질문의 80%가 클릭으로 끝난다. 화면은: 한국 선택 → 시나리오 드롭다운(안도걸 안, 김현정 안, 현행법만, 내 제안 프리셋) → 빈칸 클릭 → 그 규칙의 5층이 날짜와 상태와 같이 뜬다 → 그 위에 LLM 검색.

은행 로컬 모델 — 두 층으로 갈린다

학기 산출물은행 도입 시
데이터전부 공개 자료(법령, 법안, Circle 공시, SEC 제출)내부 데이터가 붙는다
걸리는 규제없음망분리(전자금융감독규정 제15조), 신용정보와 개인정보 국외이전 규정
모델Claude API온프레미스 한국어 오픈 모델, 또는 혁신금융서비스 경로
내 기억: 2024년 8월 금융위 "금융분야 망분리 개선 로드맵"으로 생성형 AI를 혁신금융서비스로 허용하기 시작했고 이후 은행들이 지정을 받아 쓰고 있다. 조문 번호, 날짜, 은행명은 확인 필요. 프롬프트 B로 조사한다.

설계에서 LLM을 노드 id 인용으로만 제한해 두면 모델을 갈아끼워도 구조가 안 바뀐다. 그래서 "배포 시 고려" 한 문단이면 되고 설계를 바꿀 일은 아니다.

6. 멘토 질문 (김병륜, 신한투자증권 FEP/FIX/DMA)

"한국 스테이블코인 법안과 하위규정이 계속 바뀌는 걸 전제로 시스템을 짰습니다. 규칙은 고정, 규정은 설정 파일, 설정 파일은 법안 상태를 따라 갱신합니다. 해외 관할권은 참조용으로만 둡니다. 대외계에서 거래소 규격이나 FIX 스펙이 개정될 때 실제로 이렇게 하나요, 아니면 어디서 깨지나요?"

프롬프트 A — 법령 근거 그래프의 표준과 오픈소스

아래 블록 전체를 복사

나는 한국 원화 스테이블코인 준비금 공시 규칙 15개를 법령, 계류 법안, 정부 자료, 보도, 관행의 5층 근거에 연결하는 "근거 그래프"를 만들고 있다. 지금은 JSON 파일(문서 39건, 간선 110개)이고, 간선마다 원문 인용문이 붙어 있으며 인용문이 원문에 글자 그대로 있는지 코드로 검사한다. 이걸 공개 표준과 오픈소스로 올리고 싶다. 아래를 조사해 달라.

1. Akoma Ntoso (OASIS LegalDocML)
   - 조, 항, 호, 목을 노드로 표현하는 구조와 eId(요소 식별자) 명명 규칙의 원문 규격
   - 한국 법령이나 아시아 국가 법령에 적용한 공개 사례가 있는지
   - Python으로 Akoma Ntoso를 읽고 쓰는 오픈소스 라이브러리
2. ELI(European Legislation Identifier)와 유사한 법령 URI 체계. 한국 법제처의 법령ID 체계와 대응시킬 수 있는지
3. LegalRuleML — 법 조문을 규칙(조건, 결과)으로 표현하는 표준. 실제 도구나 사례가 있는지, 아니면 논문 수준인지
4. FIBO (EDM Council, Financial Industry Business Ontology)
   - 준비자산(reserve asset), 수탁기관(custodian), 발행사(issuer), 상환(redemption)에 해당하는 클래스나 속성이 있는지, 있으면 클래스 이름과 URI
   - 스테이블코인이나 디지털자산 관련 확장이 있는지
5. 규제 변경 추적(regulatory change management)의 공개 사례나 오픈소스. 예: 영국 FCA Digital Regulatory Reporting, 미국 Federal Register API, 유럽 EUR-Lex 변경 알림. 법안 상태를 기계적으로 추적하는 공개 구현이 있는지
6. 금융권 규제 지식그래프의 공개 논문이나 사례(은행, 규제기관, 벤더 무관). 어떤 그래프 DB나 온톨로지를 썼는지
7. Python 도구 비교: networkx, rdflib, pyoxigraph, kuzu. 노드 수천 개 수준 소규모 그래프에서 도달 가능성 질의("노드 X를 제거하면 도달 못 하는 노드")를 하기에 어떤 게 맞는지

출력 형식:
- 항목마다 원출처 URL, 발행 기관, 문서 날짜, 확인 문장 인용을 붙인다
- 사실과 추론을 분리한다. 추론이면 "추론"이라고 쓴다

나는 은행 준법 담당자가 쓸 규제 검토 도구를 설계하고 있다. 도구의 검색 기능에 LLM(RAG)을 붙이려는데, 데이터는 현재 전부 공개 자료(법령, 국회 법안, 발행사 공시)다. 나중에 은행이 도입하면 내부 데이터가 붙을 수 있다. 한국 금융회사가 외부 LLM API(미국 서버)를 쓸 수 있는지, 로컬 모델이 필요한지 판단하려고 한다. 아래를 조사해 달라. 전부 한국 기준이다.
